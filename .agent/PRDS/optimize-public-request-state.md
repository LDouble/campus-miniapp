# OUSea小程序: 优化公共请求共享状态与刷新策略

**Priority:** High
**Status:** Done
**Type:** Enhancement
**Created:** 2026-08-17
**Last Updated:** 2026-08-17

## 概述

将当前分散在首页、个人中心、认证页和教务二级页中的公共请求统一接入轻量共享状态层。小程序启动时在后台预取必要数据，页面显示时优先复用仍然新鲜的数据和正在执行的请求，仅在缓存过期、用户手动刷新或业务状态发生变化时重新访问网络。

同时在微信小程序启动阶段注册版本更新管理器。微信检测并下载完新版本后，客户端立即应用更新并强制重启，避免用户继续运行旧版本。

本次重点治理以下公共数据：

- 当前平台账号：`GET /api/v1/auth/me`
- 当前会话身份：`GET /api/v1/auth/identity`
- 校园身份认证状态：`GET /api/v1/academic-verification`
- 当前身份可用教务学期：`POST /api/v1/academic/periods`
- 本科生、研究生校历：`GET /api/v1/academic/calendar`

## 用户故事

作为频繁在首页、个人中心和教务页面之间切换的用户，我希望页面能够立即复用已经获取的数据，而不是每次返回都等待相同公共接口，使页面切换更快且弱网下更稳定。

作为需要查看最新认证、学期和校历状态的用户，我希望手动刷新和真实业务变更仍能立即获取最新数据，不因客户端缓存长期展示过期状态。

## 问题背景

当前首页和个人中心在每次 `useDidShow` 时都会重新加载账号和认证状态；首页认证通过后还会重新加载学期和校历。课表、考试和选课页初次挂载时各自请求学期，课程、成绩、考试和选课请求又分别以 `/auth/identity` 作为串行前置请求。

部分页面有本地缓存，但主要用于首屏展示和失败回退，没有用于抑制仍然新鲜时的网络请求。`periods`、`identity` 和认证状态没有统一 TTL 或同飞请求合并；校历仅合并同时进行的请求，请求结束后再次显示页面仍会访问网络。

结果是普通的“首页 → 二级页 → 返回首页”会重复请求稳定的公共元数据，快速切页还可能启动多批并发的首页加载。

## 实施方案概览

新增不依赖第三方库的通用共享资源状态模块，为每类资源保存 `data`、`updatedAt` 和 `pending`，并提供以下统一能力：

- `ensure`：缓存未过期时直接返回；过期或不存在时请求网络。
- `refresh` 或 `force`：绕过 TTL，供下拉刷新、重试和明确业务变更使用。
- single-flight：相同资源已有请求进行中时复用同一个 Promise。
- `invalidate`：清除指定资源的新鲜度，使下一次读取重新请求。
- 分组失效：账号会话变化时一次清除所有会话级资源。
- 可测试时间源：TTL 边界能够通过纯 TypeScript 冒烟测试稳定验证。

在 `App.useLaunch` 中执行非阻塞预热。首页、个人中心和二级页继续维护各自的展示状态，但不再直接决定是否发送公共网络请求，而是通过共享资源入口读取。页面 `useDidShow` 可以继续执行 `ensure`，但新鲜缓存和同飞请求不会产生额外 HTTP 请求。

## 功能要求

### 共享资源基础能力

1. 相同资源在 TTL 内重复读取不得再次调用 loader。
2. 相同资源的并发读取必须复用同一个进行中 Promise。
3. 不同资源、不同教育层次的校历不得错误合并。
4. 请求失败后必须清除 `pending`，后续请求可以正常重试。
5. 请求失败不得把失败时间标记为最新成功时间。
6. `force` 必须绕过 freshness 判断，但仍应与同一个正在执行的请求合并，避免一次手动操作产生重复请求。
7. `invalidate` 只清除新鲜度或数据，不得取消其他无关资源。
8. 会话分组失效必须防止新账号复用旧账号的 `user_id`、账号资料、认证状态或教务学期。

### 启动预热

1. 在现有 `App.useLaunch` 中后台启动公共数据预热，不阻塞应用组件渲染。
2. 启动阶段的首页 `useDidShow` 与预热并发时必须复用同一批 Promise。
3. 未登录、已注销或认证未通过的用户不得无意义地请求受限教务数据。
4. 预热失败不得阻止小程序启动；目标页面继续使用现有错误和缓存回退逻辑。

### 小程序强制更新

1. 仅在微信小程序环境注册全局唯一的 `UpdateManager`，其他 Taro 构建目标不得执行微信专属逻辑。
2. 应在 App 启动时注册监听，且同一 JS 运行周期内只注册一次。
3. 微信发现新版本并完成下载后，必须立即调用 `applyUpdate()`，强制重启并切换到新版本，不提供跳过入口。
4. 新版本下载失败时，应向用户提示“新版本下载失败，请检查网络后重新打开小程序”，不得影响当前版本继续运行。
5. 更新检查由微信在冷启动时自动触发，客户端不增加轮询、定时器或业务接口。

### 当前账号与 `/auth/identity`

1. `/auth/identity` 在同一登录会话内默认只请求一次。
2. 课程、成绩、考试和选课请求继续在读取本地教务凭据前确认当前平台用户，但确认过程应复用共享 identity。
3. `/auth/me` 在短期内由首页、个人中心及其他消费者共享。
4. 用户名或头像更新成功后，应更新或失效当前账号资源，保证页面立即显示新值。
5. 登录、退出、刷新失败后重新登录、账号注销和注销后恢复使用必须切换会话代次并清除旧会话资源。
6. identity 缓存不得跨账号无条件持久化；必须与当前登录会话绑定。
7. 账号注销除清除 Storage 和共享状态外，还必须清除 `academic-credential` 模块内存中的用户凭据，避免恢复使用前敏感数据继续驻留。

### 校园认证状态

1. 首页、个人中心、认证页和社团权限检查共享认证状态与同飞请求。
2. 已认证或未认证状态采用短 TTL，避免频繁切页重复请求。
3. 审核中的认证状态采用更短 TTL，并在小程序重新进入前台后按 freshness 检查，以便感知后台审核结果。
4. 提交教务账号认证、提交学生证审核、认证成功、重新绑定、撤销身份或账号注销后，必须主动失效认证状态。
5. 认证页下拉刷新、显式重试和认证流程关键节点必须能够强制刷新。
6. 任一业务接口返回 `academic_verification_required` 时，必须立即失效可能过期的已认证状态，再进入认证引导。

### 教务学期

1. 首页、课表、考试和选课页共享同一份学期资源。
2. 学期资源必须按登录会话隔离，并设置比认证状态更长的 TTL。
3. 现有 `academicStorage` 学期快照继续承担冷启动首屏和网络失败回退，不重复建立不兼容的持久化格式。
4. 教务凭据保存、重新绑定成功、认证状态变化时主动失效学期资源。
5. 下拉刷新、错误重试和用户明确要求更新时强制刷新学期。
6. 页面普通挂载或从二级页返回首页时只执行 `ensure`，缓存新鲜时不发送网络请求。

### 校历

1. 保留本科生、研究生维度的独立缓存和本地持久化。
2. 在现有同飞请求 Map 基础上增加 freshness TTL 和强制刷新入口，或迁移到统一共享资源实现。
3. 首页、校历页和空教室页共享相同教育层次的校历请求。
4. 普通页面显示使用新鲜缓存；下拉刷新和用户切换教育层次后首次加载可以强制更新。
5. 网络失败继续回退到现有本地校历缓存。

### 页面接入

1. 首页 `useDidShow` 可以继续刷新页面展示，但公共资源必须通过共享入口读取，快速重复显示不得启动多轮相同公共请求。
2. 个人中心不得在每次显示时无条件重新请求 `/auth/me` 和认证状态。
3. 认证页普通重新显示复用短期状态，提交、回跳和下拉刷新按业务要求强制更新。
4. 课表、考试、选课页面首次挂载优先使用共享学期；已有缓存时不得无条件请求 periods。
5. 课程、成绩、考试和选课业务数据本身仍沿用现有缓存、认证成功刷新信号和手动刷新策略，本次不把高频业务数据错误地改成长期公共缓存。
6. 资料页、注销页和其他直接读取 `/auth/identity` 的页面统一改用共享 identity。

## 建议有效期

具体常量在实现与测试阶段统一定义，初始建议如下：

- `/auth/identity`：当前登录会话内有效，直到会话失效。
- `/auth/me`：5 分钟；资料更新成功后立即失效或写回。
- 已认证或未认证状态：1 分钟。
- 审核中认证状态：30 秒。
- 教务学期：30 分钟。
- 校历：30 分钟；手动刷新始终绕过 TTL。

有效期不得散落在页面组件中，应由对应资源模块集中维护。

## 非功能要求

- 不引入 Redux、Zustand 或其他第三方状态库。
- 保持 Taro 4.1.11、React 18 和微信小程序运行环境兼容。
- 不改变现有后端 API、请求体、认证头和 OpenAPI 类型。
- 不缓存教务密码到新的位置，不把密码、Token 或其他敏感数据写入日志。
- 共享状态层必须保持模块依赖单向，避免 `auth → state → api/client → auth` 循环依赖。
- 页面仍应能够在共享状态请求失败时展示既有本地缓存和错误反馈。
- 请求数量优化不得导致跨用户数据污染或认证撤销后继续使用旧权限。

## 技术实现

### 共享资源模型

新增纯逻辑的共享资源工厂，资源实例保留最近成功值、更新时间和进行中 Promise。工厂自身不导入 API 客户端，API 或 repository 层向其传入 loader，从而避免循环依赖。

共享资源支持按组注册失效回调。`auth.clearSession()` 只依赖纯状态基础模块并触发会话组失效；具体账号、认证和学期模块可以依赖 API 客户端，不形成反向依赖。

### 页面与状态边界

本次共享状态的主要职责是控制请求复用和 freshness，不要求一次性重写所有页面为全局响应式渲染。页面仍可在 Promise 完成后写入自己的 React state，这能控制改造风险，并保持当前加载态与错误处理。

如实现过程中发现首页和个人中心确实需要跨页面即时订阅账号更新，可以在共享资源上增加最小订阅接口；不得为此引入完整状态管理框架。

### 本地缓存关系

- identity 仅保存在当前 JS 会话内，不新增长期存储。
- current user 与认证状态默认仅作会话内短期缓存。
- periods 继续复用 `academicStorage` 中按平台用户隔离的快照作为冷启动种子和失败回退。
- calendar 继续复用 `campus.academicCalendar.v1.*` 存储及 `updatedAt`。

### 生命周期

Taro `useLaunch` 对应 App `onLaunch`，用于启动非阻塞预热；`useDidShow` 在页面首次显示、从二级页返回和重新进入前台时都会触发，因此页面显示阶段只允许调用带 freshness 判断的 `ensure`，不能继续无条件强制请求。

参考：[Taro Hooks 文档](https://docs.taro.zone/docs/hooks)

本次不新增或修改后端接口，不涉及数据库变更。所有优化均发生在小程序客户端的请求编排、缓存和失效层。

## 测试要求

### 共享资源测试

- TTL 内命中缓存，TTL 边界到期后重新请求。
- `force` 绕过新鲜缓存。
- 相同资源并发请求只执行一次 loader。
- 不同 key 或不同教育层次互不合并。
- loader 失败后清除 pending，下一次能够重试。
- invalidate、资源分组失效和会话切换后重新请求。
- 旧会话请求晚返回时不得写入新会话资源。

### 业务接入测试

- 启动预热与首页首次显示并发时，账号、认证、学期和校历各自最多请求一次。
- 首页进入课表再返回首页，TTL 内不重复请求账号、认证、学期和校历。
- 课表、考试和选课依次进入时共享学期资源。
- 课程、成绩、考试和选课依次请求时共享 `/auth/identity`。
- 认证提交、重新绑定、身份撤销、账号注销和重新登录后，对应资源重新请求。
- 认证审核中经过短 TTL 或重新进入前台后能够获得后台审核变化。
- 下拉刷新和显式重试会绕过 TTL，但不会制造相同资源并发重复请求。
- 本科与研究生校历缓存和请求保持隔离，失败时继续回退本地缓存。

## 验收标准

1. 冷启动可以后台预取公共数据，且不阻塞首屏渲染。
2. 同一会话内 `/auth/identity` 不再为每个教务业务请求重复访问网络。
3. 首页与个人中心频繁切换时，TTL 内不重复请求 `/auth/me` 和认证状态。
4. 首页、课表、考试和选课在 TTL 内共享学期结果。
5. 首页、校历和空教室在 TTL 内共享相同教育层次的校历结果。
6. 相同资源同时被多个页面读取时只产生一次 HTTP 请求。
7. 下拉刷新、显式重试和真实业务变更仍能获取最新数据。
8. 登录账号切换、注销和恢复使用后不会展示或复用旧账号数据。
9. 认证审核中的后台变化可以在合理时间内被感知。
10. 现有教务缓存回退、认证成功自动刷新和页面错误反馈不回归。
11. 相关 lint、类型检查、冒烟测试和微信小程序构建通过。
12. 微信小程序检测到已下载的新版本后立即强制重启并应用更新；下载失败时给出明确提示。

## 风险与回滚

- 风险：TTL 过长导致认证或学期变化短暂不可见。通过动态短 TTL、业务事件主动失效和手动强刷降低风险。
- 风险：会话切换时旧 Promise 晚返回污染新会话。共享资源需要记录 generation，仅允许当前代次提交结果。
- 风险：在 API、状态和 auth 模块之间形成循环依赖。共享资源基础模块保持纯逻辑，具体 API 单向依赖它，auth 仅调用纯分组失效入口。
- 风险：页面调用仍传递错误的 force 语义，导致重复请求未完全消失。通过全局调用点检索、结构测试和 Network 手动验证覆盖。
- 回滚：各 API/repository 可恢复为直接 loader 调用，页面本地 state、现有存储格式和后端接口均未改变，不需要数据迁移。

## 发布说明

本次为客户端请求性能和状态一致性优化，不涉及后端或数据库发布。上线后重点观察首页显示耗时、公共接口请求量、401/认证错误率，以及账号切换和认证状态更新是否正确。
