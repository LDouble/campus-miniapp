# 小程序：校园生活四业务差异化 UI/UX 重设计

**Priority:** High
**Status:** Done
**Type:** Enhancement
**Created:** 2026-07-26
**Last Updated:** 2026-07-26

## 概述

重新设计校园生活聚合页中的社区、跑腿、二手、拼车四类业务。四类业务共享统一的校园品牌基线、导航逻辑、状态反馈与触控规范，但不再共享同一种页面、卡片或筛选模板：

- 社区是内容消费场景，强调作者、正文、图片和互动。
- 跑腿是即时任务场景，强调报酬、时效、状态和取送路线。
- 二手是商品决策场景，强调图片、价格、标题和交易状态。
- 拼车是出行决策场景，强调出发时间、起终点、余座和参与人数。

本次重构仅调整小程序信息架构、视觉和交互，不改变现有服务端接口及业务状态机。社区板块继续完全通过服务端接口获取，不在客户端硬编码板块名称、标识或数字 ID。

## 用户故事

**作为** 中国海洋大学在校学生
**我希望** 进入不同校园生活业务时，能立即看到该业务最关键的数据并快速完成发布、浏览和查看详情
**从而** 减少识别成本，在几秒内判断一条内容、任务、商品或行程是否值得进一步操作

## 现状与问题

### 信息层级

- 当前首屏连续出现页面标题、搜索入口、一级导航、二级导航和业务 Hero，内容入口下沉。
- 一级业务切换与二级筛选视觉相近，用户需要额外判断当前所处层级。
- 搜索在顶部和内容区重复表达，空间使用效率不高。

### 业务差异

- 跑腿与拼车使用相近的结构化通用卡片，任务时效和行程时间的视觉优先级不足。
- 二手已采用双列商品卡，但价格、成色信息和交易状态仍可进一步清晰。
- 社区动态卡的作者、板块、正文、图片、互动之间缺少更鲜明的阅读节奏。

### 交互效率

- 发布入口在社区和其他业务中的位置与形态不一致。
- 加载、空状态、错误状态缺少统一的骨架与反馈节奏。
- 动态板块较多时，横向选择器需要更清楚地区分根板块和子板块。
- 搜索、板块和业务条件缺少清晰的筛选层级；所有条件若堆在同一横向滚动区，会造成选中状态和数据范围难以理解。

## 设计目标

1. 用户在进入页面后 1 秒内确认当前业务。
2. 每种业务卡片只设置一个第一视觉焦点。
3. 主要操作的触控区域不小于 88rpx × 88rpx。
4. 正文与背景的普通文本对比度不低于 4.5:1。
5. 首屏减少一个重复信息层级，让首条真实业务数据更早出现。
6. 社区板块名称、描述、层级和 ID 全部来自服务端。
7. 保持现有列表、搜索、分页、发布、详情、点赞、评论和业务操作链路可用。
8. 筛选条件与接口能力一一对应，并能随时看见、单项移除和一键重置。

## 非目标

- 不新增或修改后端接口。
- 不改变跑腿、二手、拼车和社区的状态机。
- 不在本轮引入新的第三方 UI 组件库。
- 不为视觉效果增加大体积位图背景或不可控的网络字体。
- 不将四个业务强行做成完全一致的卡片模板。
- 不提供接口不支持、点击后仅改变样式却不改变数据范围的假筛选。

## 视觉系统

### 全局基线

- 风格：清爽、现代、轻量，使用克制的层次和柔和背景，不采用重度玻璃拟态。
- 页面背景：`#F5F7FA`。
- 主文本：`#17212B`。
- 次文本：`#667085`。
- 分割线：`#E6EAF0`。
- 卡片背景：`#FFFFFF`。
- 大圆角：32rpx；卡片圆角：24rpx；标签圆角：999rpx。
- 阴影：仅用于悬浮发布按钮或重点卡片，常规列表优先使用边框和留白建立层次。
- 字体：使用系统字体栈，数字开启等宽数字特性时优先保证时间、金额稳定对齐。
- 动效：点击反馈 150–200ms；遵守 `prefers-reduced-motion`，避免持续动画。
- 图标：使用 SVG，不以 Emoji 作为功能图标。

### 业务主题

| 业务 | 主色 | 辅助色 | 第一视觉焦点 | 页面结构 |
| --- | --- | --- | --- | --- |
| 社区 | `#4F46E5` | `#EEF2FF` | 正文与图片 | 单列内容流 |
| 跑腿 | `#D97706` | `#FFF7E8` | 报酬与截止时间 | 高密度任务卡 |
| 二手 | `#E85D4A` | `#FFF0ED` | 商品图与价格 | 双列商品瀑布式网格 |
| 拼车 | `#2563EB` | `#EDF4FF` | 出发时间、路线与余座 | 行程时间轴卡片 |

业务主题色只用于选中态、关键数字和主操作，状态色仍遵循统一语义：

- 成功或可进行：`#14804A`。
- 警告或临近截止：`#B54708`。
- 错误或已取消：`#C4320A`。
- 中性或已结束：`#667085`。

## 信息架构

### 聚合页顶层

1. 自定义导航栏：折叠后显示当前业务名称和搜索按钮。
2. 一级业务切换：社区、跑腿、二手、拼车，采用固定四等分标签，不横向滚动。
3. 业务上下文区：根据业务类型呈现不同的紧凑标题、说明和主操作。
4. 搜索：只保留一个真实输入区；导航栏搜索按钮负责聚焦该输入区，不重复创建第二套搜索。
5. 内容区：紧接搜索或筛选区展示真实服务端数据。
6. 发布入口：四个业务均提供一致位置的悬浮主操作，但颜色和文案跟随业务。

## 筛选系统

### 通用布局原则

- 搜索与筛选分成两个层级：搜索框负责关键词，条件栏负责结构化条件。
- 首屏默认只占一行条件栏，不把所有表单控件平铺在列表上方。
- 高频条件使用可横向滚动的快捷筛选；低频或复合条件放入底部筛选面板。
- “筛选”按钮显示已生效条件数量；无条件时不显示数字角标。
- 已生效条件在结果区上方以摘要标签展示，每项可单独移除，并提供“清除全部”。
- 应用筛选后回到列表顶部并从第 1 页重新请求，禁止把新条件错误追加到旧分页数据。
- 关闭筛选面板不应用草稿值；点击“查看结果”才提交，点击“重置”清空当前业务全部结构化条件。
- 切换业务时各自保留本次会话中的筛选条件，避免在四类业务之间串值。
- 筛选面板底部操作区固定在安全区上方，主按钮文案显示“查看结果”，不使用含糊的“确定”。

### 条件能力矩阵

| 业务 | 首屏快捷筛选 | 底部筛选面板 | 接口字段 | 布局说明 |
| --- | --- | --- | --- | --- |
| 社区 | 服务端根板块 | 当前根板块的服务端子板块 | `parent_section_id`、`section_id`、`keyword` | 根板块和子板块分成两级，不再把整棵树压成同一排 |
| 跑腿 | 当前范围“待接任务” | 本期不展示额外条件 | `keyword` | 公开接口目前只有关键词条件，固定范围以说明条表达，不伪装成可切换筛选 |
| 二手 | 不限价格、50 元内、50–200 元、200 元以上 | 自定义最低价与最高价 | `min_price_cents`、`max_price_cents`、`keyword` | 快捷价格采用单选，面板内使用双输入并校验上下限 |
| 拼车 | 今天、明天、选择日期；1 人、2 人、3 人及以上 | 起点、终点、出发日期、所需座位 | `origin`、`destination`、`departure_date`、`seats_needed`、`keyword` | 路线条件成对排列，日期与人数使用独立分组 |

### 社区筛选布局

- 第一行只展示服务端返回的启用根板块，选中根板块时查询其自身与启用子板块。
- 第二行仅在当前根板块存在启用子板块时出现，首项为根板块聚合范围，其余为子板块精确范围。
- 根板块使用文字标签和下划线表达导航层级；子板块使用轻量胶囊表达筛选层级。
- 根板块或子板块名称、数量、slug 和 ID 均不得写入客户端常量。
- 切换根板块时自动清除不属于新根板块的子板块选择，并从第 1 页重新加载。

### 跑腿筛选布局

- 搜索框下方使用紧凑说明条显示“当前展示全校待接任务”，避免把固定接口范围包装成可点击标签。
- 说明条右侧展示结果数量，不再增加没有接口支撑的“距离最近”“高报酬”“即将截止”等按钮。
- 后续若服务端增加报酬、截止时间或区域查询参数，可在底部筛选面板内增量开放，不改变列表主体结构。

### 二手筛选布局

- 搜索框下方常驻一行价格快捷项，默认选中“不限价格”。
- 自定义价格入口位于快捷项末尾，点击打开底部筛选面板。
- 最低价和最高价均使用元为展示单位，提交请求前转换为分。
- 最低价不得大于最高价；输入非法时在字段附近显示错误，不关闭面板。
- 应用自定义区间后，快捷项显示实际摘要，例如“¥80–¥300”，而不是继续显示“自定义”。

### 拼车筛选布局

- 首屏快捷栏优先展示日期，其次显示“筛选”按钮及有效条件数量。
- “今天”和“明天”根据本地当前日期动态计算，只作为时间快捷操作，不属于服务端业务硬编码。
- 起点与终点在底部面板内纵向排列，中间使用方向图标明确路线关系。
- 所需座位使用单选分段按钮；“3 人及以上”请求值按接口现有 `seats_needed` 语义提交为 3。
- 应用后在列表标题下展示路线、日期和人数摘要；单项移除时只清除对应字段并重新请求。

### 筛选状态与异常

- 请求进行中禁用重复应用，保留面板中的当前值。
- 筛选结果为空时展示当前条件摘要和“清除筛选”主操作。
- 接口失败时保留已应用条件，重试使用完全相同的查询参数。
- 输入条件在客户端做基础校验，服务端错误信息仍通过统一 API 错误组件展示。

### 社区

- 一级业务切换下方展示服务端动态板块。
- 根板块为主要选项，子板块使用较弱视觉权重；根板块查询聚合自身及启用的子板块。
- 动态卡片顺序为作者信息、板块标签、标题/正文、图片、互动数据。
- 一图使用横向大图，两图使用双列，三图使用三列。
- 点赞操作提供即时视觉反馈，评论点击进入详情。

### 跑腿

- 头部以“待接任务”及当前结果数量表达当前列表语义。
- 卡片顶部突出报酬，右侧展示任务状态。
- 中部用明确的取件点 → 送达点路线结构，不复用拼车的视觉语言。
- 截止时间采用紧迫性表达，临近截止时提高警示色权重。
- 卡片底部提供“查看任务”方向提示，避免误以为点击只查看路线。

### 二手

- 保持双列商品网格，图片占卡片主要面积。
- 价格紧邻商品标题，交易状态覆盖在图片上。
- 描述最多两行，弱化低价值重复文案。
- 无图片时使用轻量品牌占位，不显示虚构商品图。
- 图片使用懒加载，容器预留固定比例，避免列表跳动。

### 拼车

- 按出发日期在客户端分组展示，不新增服务端接口。
- 卡片顶部突出出发日期和时间，余座为第二关键指标。
- 起点和终点使用横向路线轨道，地点长文本允许省略。
- 已参与人数与总座位在同一区域呈现。
- 不展示服务端不存在的价格、车型或司机认证信息。

### 详情页

- 社区详情延续内容阅读结构，评论输入区固定在安全区上方。
- 跑腿详情先展示报酬、状态和截止时间，再展示路线和任务说明。
- 二手详情先展示图片轮播、价格和交易状态，再展示描述与交易操作。
- 拼车详情先展示时间和路线，再展示余座、参与情况和行程说明。
- 所有状态操作沿用现有权限、版本号和幂等逻辑，不因改版改变业务行为。

## 交互要求

### 业务切换

- 点击一级标签后保留本地最近访问业务。
- 切换时立即更新主题色、标题、搜索提示和列表结构。
- 不使用大幅滑动转场，避免小程序低端设备掉帧。

### 搜索

- 导航栏搜索按钮滚动到内容锚点并聚焦真实输入框。
- 回车和“搜索”按钮行为一致。
- 有输入时提供明确清除入口，清除后恢复默认列表。
- 搜索结果标题展示关键词和结果数量。
- 搜索和结构化条件共同生效；结果标题和空状态必须同时反映当前条件。

### 加载与反馈

- 初次加载显示与当前业务卡片形态一致的骨架屏。
- 分页按钮避免重复点击；加载时显示进行中状态。
- 错误状态提供清晰错误说明和重新加载入口。
- 空状态文案与当前业务匹配，不使用一套泛化文案覆盖四个业务。

### 无障碍与触控

- 图标按钮提供 `ariaLabel`。
- 交互区域不小于 88rpx，紧凑文字按钮通过透明内边距扩充热区。
- 关键信息不只依赖颜色传达，同时保留文字状态。
- 文本字号原则上不低于 24rpx，正文使用 28–30rpx。

## 数据约束

### 社区动态板块

- 唯一来源：`GET /api/v1/campus-circle/sections`。
- 客户端不得硬编码板块名称、slug、数值 ID、父子映射和默认固定板块。
- 服务端无启用板块时展示可恢复的空状态，不偷偷回退到客户端常量。
- 根板块、子板块和禁用状态继续沿用现有接口语义。

### 列表数据

- 社区：`GET /api/v1/campus-circle/posts`。
- 跑腿：`GET /api/v1/errands`。
- 二手：`GET /api/v1/marketplace/listings`。
- 拼车：`GET /api/v1/carpool/trips`。
- 所有关键视觉数据必须来自响应字段；无字段时不编造展示内容。

### 筛选参数

- 社区仅提交 `keyword`、`section_id` 或 `parent_section_id`，根板块与子板块参数互斥。
- 跑腿公开列表本期仅提交 `keyword`。
- 二手提交 `keyword`、`min_price_cents`、`max_price_cents`。
- 拼车提交 `keyword`、`origin`、`destination`、`departure_date`、`seats_needed`。
- 切换或清除条件时页码重置为 1；加载更多必须复用当前完整筛选快照。

## 技术实现

### 架构方案

- 继续使用 Taro React 与 TypeScript。
- 保留 `CommunityPage` 作为四业务聚合容器。
- 将业务主题、文案和图标元数据集中为仅包含视觉语义的配置；社区板块业务数据不进入该配置。
- 将社区动态卡、跑腿任务卡、二手商品卡和拼车行程卡拆分为独立的业务组件或清晰的局部组件。
- 筛选状态采用每个业务独立的类型，不使用字段含义模糊的通用键值对象。
- 底部筛选面板共享遮罩、标题、安全区和操作栏骨架，条件内容由业务组件分别渲染。
- 列表请求继续由现有 repository 负责，视图层不直接拼接请求地址。
- 使用 Taro `Image` 的 `lazyLoad` 和固定容器比例控制商品与社区图片性能。
- 小程序端不引入 Web 专用悬停逻辑，点击反馈使用 `hoverClass`。

### Taro 与微信端注意事项

- 横向板块使用 `ScrollView scrollX`，内部保持 `white-space: nowrap`。
- `ScrollView` 不承担整页纵向滚动，继续使用页面原生滚动与下拉刷新。
- 列表 `key` 使用服务端稳定 ID。
- 避免在渲染期创建大对象或重复递归板块树，板块映射继续使用 `useMemo`。
- 所有时间继续通过统一格式化函数处理，避免 iOS 日期解析差异。
- 底部面板使用小程序兼容的 `View` 层级和受控表单，不依赖 Web Portal。

## 风险与控制

- **现有工作区存在未提交改动**：只在本任务文件范围内增量修改，不覆盖或回滚用户已有更改。
- **四类视觉差异导致样式膨胀**：共享基础 token，只为业务关键信息结构建立独立样式。
- **详情操作回归**：不重写 repository 和状态机，仅调整内容排序与视图组件。
- **服务端板块回退风险**：保留现有动态板块加载和无配置空状态，禁止客户端默认板块常量。
- **低端设备性能**：减少大面积模糊、阴影和持续动画，图片懒加载并限制列表图片数量。
- **筛选能力与界面不一致**：仅开放 OpenAPI 已支持的查询参数；跑腿未支持条件以范围说明代替可点击控件。
